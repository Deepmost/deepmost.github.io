一位消费者打电话催发货，听起来只是客服查一下订单、回复一句进度。但在一家大型企业里，这个请求可能要区分整机、配件和赠品，跨越电商平台、订单、仓库、物流、审批与赔付等多个系统，最终形成 260 多个处理步骤。

这正是企业级 AI 与聊天机器人的区别：**聊天机器人解决的是“怎么回答”，企业 Agent 必须解决“怎么把事情办完”。**

《硅谷 101》E248 邀请阿里瓴羊 CEO 朋新宇，从客服、营销、销售等真实案例出发，讨论 AI 如何进入企业，也回答了一个很有争议的问题：FDE（Forward Deployed Engineer，前沿部署工程师）究竟是一个新岗位，还是驻场开发换了一个更时髦的名字？

听完这期节目，我最大的感受是：FDE 的价值并不来自新 title，而是交付对象发生了变化——过去交付功能和系统，现在要交付可以持续度量的业务结果。

## 一、FDE 不是驻场开发换名，而是从交付功能转向交付结果

传统的软件交付通常有一个明确的终点：需求开发完成，系统通过验收，项目就可以结项。驻场运维关注的则是系统是否稳定、接口是否正常、故障能否及时恢复。

企业 Agent 上线后，工作却才刚刚开始。企业关心的不是“Agent 能不能运行”，而是：

- 客服能否更快解决问题、减少投诉和赔付；
- 销售能否覆盖更多客户、提高转化；
- 营销投放能否获得更高 ROI；
- 同样的成本下，业务效果能否超过原来的人工作业。

因此，FDE 不能只懂部署和运维。节目把这类人才需要的能力概括成三个维度：

1. **AI 的锐度**：了解模型、Agent、上下文、记忆和评测，知道什么环节适合机器，什么环节需要人工介入。
2. **行业的深度**：理解客户真正的业务流程，知道客服、销售或投手每天具体怎么工作。
3. **数据的宽度**：能够利用数据建立参照系，判断业务是在变好还是变差，并据此调整系统。

这三个能力最终服务于三条原则：以业务结果为导向，以企业数据为基座，以最佳岗位实践为预设。

所以，一个人不会因为职位改叫 FDE 就变得更值钱。真正稀缺的是能够进入复杂现场、找出高价值问题，并让 AI 最终拿到结果的人。

## 二、260 步催发货，暴露了企业 AI 的真正难点

节目里最有代表性的案例，是一个 3C 家电企业的“催发货”流程。

消费者的诉求可能是少发了一台空调，也可能是缺少一个配件，或者承诺赠送的电饭煲没有收到。客服接到问题后，需要核查订单、判断商品类型、联系对应仓库、处理跨平台信息，有时还要补下订单、发起赔付或转交其他部门。所有情况加起来，完整流程有 260 多步，覆盖了 95% 以上的常见问题。

这件事说明，客服的核心价值并不是态度友好地说“我帮您查一下”，而是理解企业如何运转，并真正解决问题。

普通聊天机器人擅长生成自然语言，却未必能访问正确的数据、调用内部系统、遵守审批规则，更不一定知道下一步该找谁。要让 Agent 接管催发货，必须把散落在组织中的流程、知识、系统和权限连接起来。

因此，企业选择 AI 场景时，不应该先问“哪个模型最强”，而应该先找三类地方：

- **耗人最多**：例如大量重复的接线、外呼和投诉处理；
- **耗钱最多**：例如赔付、止损、广告投放和素材试验；
- **耗时最多**：例如跨系统查询后，要几小时甚至几天才能回复客户。

这些场景有清晰边界、足够高的重复量，也有成本、时效、转化率和满意度等指标，最容易验证 AI 是否创造了真实价值。

## 三、企业部署 Agent，更像招聘员工，而不是安装软件

节目里有一个很形象的类比：传统软件交付像给员工安装一套工具，企业 Agent 则更像招聘了一位已经具备五到十年经验的数字员工。

这名“员工”带着通用技能进入公司，但要真正开始工作，企业仍然需要给它四样东西：

- 具体的业务目标；
- 企业内部的数据和知识；
- 调用系统与执行任务的权限；
- 审批、投放、赔付等事项的裁量边界。

如果知识库混乱、数据口径不一致、业务流程没有沉淀，即使模型能力很强，Agent 进入企业后也会“傻眼”。这就是节目反复强调的 **Data for Agent**：过去的数据平台主要给管理者看报表，未来的数据还要能被 Agent 理解、检索和调用。

数据的价值也不只体现在知识库。节目提到一家多平台投放的企业，最优秀的投手在三个月里进行了一万多次价格调整，而普通投手只有一百多次。过去依靠师傅带徒弟，很难完整复制这种隐性的工作经验；现在可以把历史行为全部数字化，让 AI 从中总结规律。

这个过程可以拆成四步：

> 学习数据 → 建立模型 → 执行任务 → 根据好坏案例持续迭代

企业真正的竞争力因此不只是“用了哪个模型”，还包括是否沉淀了高质量的工作数据，能否把最佳员工的经验转化为 Agent 可学习、可评测、可进化的能力。

## 四、标准化与个性化，并不是二选一

传统企业软件经常陷入一个问题：每家公司都认为自己的流程独一无二，于是供应商不断增加定制功能，项目越做越长，最后变成以“人天”为单位出售开发资源。

但如果每个客户都从零开发一套系统，供应商和客户都很难获得规模效应。节目里提出的思路，是用“4+X”来处理这个矛盾：

- “4”是营销、销售、客服、运营四类预设 Agent，内置相应岗位的通用最佳实践；
- “X”是每家企业独有的数据资产、上下文、系统权限和管理边界。

标准化的是解决问题的方法和工作环境，个性化的是企业数据以及每一次具体决策。

例如营销 Agent 都要经历数据采集、分析、决策、调整和复盘，但不同品类、渠道、周期的转化率完全不同。供应商无需承诺统一提升十倍，而是根据客户历史数据建立基线，通过 MVP 和 A/B 测试验证增量价值。

这让我重新理解了企业 Agent 的产品化：**它不是把所有企业塞进同一条僵硬流程，而是用标准化的能力底座，处理不断变化的个性化任务。**

## 五、中国式 FDE，往往要先打地基再盖楼

中美企业级 AI 的一个重要差异，是信息化基础不同。

很多美国企业长期使用 Salesforce、SAP 等软件，已经形成相对稳定的工作流和数据标准。FDE 进入现场后，可以更多地聚焦于发现高价值问题、连接现有系统和部署 AI 能力。

中国企业则大量依赖自建 IT 系统以及淘宝、天猫、京东、抖音、企业微信等平台。不同部门和渠道的数据口径不一，流程也未必已经标准化。因此，中国的 FDE 经常不能只做“最后一公里”，而是需要从数据治理、流程梳理和系统连接开始，既打地基，也盖楼和装修。

这也是中国式 FDE 看起来更像交付团队的原因。但它与传统外包仍有一个关键区别：传统外包接收的是一张功能清单，FDE 首先要与 CEO、业务负责人和一线员工一起，找出当前最值得解决的问题。

客户说“我要开发一百个功能”，并不等于这些功能有价值。更重要的问题是：销售、营销和客服中，哪里最耗人、耗钱或耗时？哪个问题解决后，能直接反映在收入、利润或人效上？

FDE 的起点不是需求列表，而是业务诊断。

## 六、真正困难的不是上线，而是组织改变

节目分享了一个制造业销售 Agent 的案例。过去，销售人员每天要规划拜访路线、准备客户材料，见面后还要录入系统并花时间复盘。Agent 将事前规划、事中辅助和事后跟进串联起来，试点地区从相对落后变成了企业内部的先进区域。

这个结果听起来很直接，项目却做了一年多。时间主要没有花在写代码上，而是花在熟悉岗位、推动观念转变、建立模型和训练 Agent 上。真正的系统上线反而是较快的一部分。

原因在于，Agent 改变的不只是一套工具，还会改变预算归属、部门协作、工作评价和人的职责。IT 部门可能追求技术先进性，业务部门关心实际效果，但两边的预算和目标未必统一。涉及这种“生产关系”的项目，仅靠基层员工自下而上推动很容易卡住。

节目观察到，推进顺利的项目通常由企业一号位自上而下推动。因为只有一号位才能同时调动业务、IT、财务和人力资源，按总账而不是部门小账做决策。有一位董事长甚至一年亲自给员工讲了十多场 AI 培训，先完成自己的认知转变，再推动整个组织行动。

这也解释了为什么企业 AI 不能只看技术可行性。一个准确率不错的 Agent，如果没有清晰的责任人、审批边界和复盘机制，仍然无法进入生产环境。

## 七、Agent 不是一次性上线，而是需要“带教”和灰度上岗

企业不会让一个新员工第一天就接管全部客户，Agent 也不应该如此。

节目介绍了一种一周左右的灰度上岗方式：第一天先接管凌晨零点到两点的低峰流量，把风险控制在较小范围；复盘并调整后，第二天进入中午高峰，接受完整压力测试；随后再逐渐扩大到八小时乃至全天。

这里有一个很重要的细节：高峰测试不是随机抽取十分之一的请求，而是接管整个时间段，只有完整流量才能暴露异常边界。团队每天既要看投诉和失败案例，也要找出 Agent 已经优于人的部分，然后继续调整技能、上下文和规则。

因此，FDE 也很难是一个全能的孤胆英雄。节目中的实践更接近一个三类角色组成的团队：

- **业务分析与行业专家**：梳理流程、定义目标、设计评测集；
- **AI 架构师**：把业务问题翻译成模型、工具、工作流和人机协作方案；
- **岗位标杆与 AI 教练**：由首席客服、销冠、优秀投手等持续复盘和训练 Agent。

随着项目成熟，外部团队可以逐渐后退，企业内部最优秀的业务人员则成为 Agent 的管理者和教练。

## 八、企业最后关心的不是 Token，而是总账

企业采购 AI 时，最现实的问题仍然是：这笔账算不算得过来？

节目提到两类常见商业模式：

1. **按工作量或坐席收费**：用低于原有人力成本的投入，达到不低于原来的服务效果。
2. **按效果收费**：以历史转化率、投放 ROI 等作为基线，对 Agent 创造的增量价值进行分成。

这两种模式都要求先建立评测基准，再在客户真实的数据和业务单元中做最小价值验证。企业愿意持续续费，比一份漂亮的概念验证更能说明项目是否有效。

同样，老板通常不会长期纠结一次任务用了多少 Token，正如买电脑的人最终关心的是工作能否完成。真正要算的是总账：Agent 减少了多少人力，缩短了多少处理时间，提高了多少收入或利润。

这并不意味着模型成本不重要，而是模型选择应由交付团队进行工程化优化。复杂任务可以使用更强模型，稳定和简单的环节可以使用更高性价比的模型。企业要的是稳定的工作输出，而不是每次都自动追逐最新版本。

当模型升级时，也不能简单切换 API。新的模型需要重新测试，并确认它与企业流程、权限和管理边界仍然匹配。模型进步是长期利好，但生产环境中的升级必须受控。

## 九、AI 时代，人的工作会从执行转向定义与管理

节目没有把企业 Agent 描述成简单的“机器替人”。更现实的变化是岗位发生分层：重复执行工作会被 Agent 接管，而一部分人将向上成为内部 FDE 或 AI 教练。

过去，一位客服主管的成长可能是处理更复杂的投诉；未来，他的价值可能是管理十个客服 Agent，分析异常案例，设计新技能，让整个团队覆盖远超个人上限的工作量。IT、CIO、CTO 团队也不再只是等待业务提交清晰需求，而要主动理解业务、发现问题，并负责数字员工的上岗和运营。

对个人来说，值得培养的仍然是那三个维度：AI 锐度、业务深度和数据宽度。尤其是数据能力，并不只是会做报表，而是知道如何建立参照系：

- 与过去同比，判断趋势是否健康；
- 与竞品或其他产品对比，判断相对位置；
- 看结果在整体中的占比，判断它是否真正重要。

嘉宾认为，从当前实践看，技术人员向业务走可能比纯业务人员补齐技术更容易一些。但无论从哪边出发，都不能只停留在原来的单一专业里。

行业经验也不会因为 AI 消失。对 To B 业务来说，它仍然是一种壁垒，只是年轻人可以借助 AI 和已有最佳实践，把过去十年才能积累的知识压缩到一两年。差异将来自谁更善于站在前人的肩膀上，而不是谁坚持从零摸索。

## 十、我的思考：FDE 的本质是对“最后一公里”负责

听完这期节目，我认为 FDE 与传统驻场开发确实有重叠：都需要深入客户现场、理解系统、协调不同角色，也都会遇到大量脏活和复杂约束。

但二者不能因此被简单画上等号。区别不在“是否驻场”，而在责任边界：

> 传统交付对功能是否完成负责，FDE 对 AI 是否在真实业务中持续创造结果负责。

这意味着 FDE 要同时面对技术、业务和组织三个系统。模型可能不够稳定，企业数据可能很乱，流程可能只存在于老员工脑中，不同部门也可能有互相冲突的目标。任何一层没有打通，Agent 都只能停留在 Demo。

我也看到三个需要保持警惕的边界。

第一，不是所有问题都适合 Agent。没有高频重复、没有清晰边界、也无法建立评测指标的工作，很难靠工程手段稳定交付。

第二，标准化不能变成忽视企业差异。预设 Agent 可以提供岗位能力，但企业自己的数据、权限和制度仍然决定了它能做什么。所谓“开箱即用”，在大型企业里往往只意味着缩短起点，而不是跳过治理过程。

第三，业务结果不能只看短期降本。如果企业只把 Agent 当成裁员工具，员工会天然抵触，组织也很难贡献高质量经验。更可持续的方式，是让人从重复执行者转为目标制定者、异常处理者和 Agent 教练。

## 总结

“催发货要跑 260 步”看起来是一个夸张的细节，却准确揭示了企业 AI 的现实：真正困难的从来不是让模型说一句正确的话，而是让它在复杂组织中拿到数据、遵守规则、调用系统、承担任务，并交付可以度量的结果。

因此，企业级 AI 的竞争最终不会只停留在模型参数上。模型能力会逐渐成为公共基础设施，真正拉开差距的是：

- 企业是否拥有可供 Agent 使用的数据基座；
- 是否能找到值得解决、可以算账的业务问题；
- 是否有能力把最佳岗位经验变成数字员工的技能；
- 是否愿意调整组织，让人和 Agent 形成新的协作关系。

从这个角度看，中国式 FDE 不是一个突然出现的新职业，而是客户成功、数据治理、行业咨询和 AI 工程在企业现场的重新组合。它的终点也不是“把 Agent 部署上去”，而是让数字员工真正上岗，并且一天比一天工作得更好。
